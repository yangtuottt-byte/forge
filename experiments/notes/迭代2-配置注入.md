## 一、学到的核心概念(用自己的话)

### 1. 配置注入解决什么问题 ⭐
**硬编码配置的三大罪**:
1. 换环境(开发→测试→生产)要改代码 push 一次
2. **密钥写死在代码里 = 必然进 Git = 泄露**
3. 多机器密码不一致的运维地狱
**注入做法**:代码只留默认值,真实值从环境注入,优先级:
```
真实环境变量(export/容器注入) > .env 文件 > 代码默认值
```

### 2. 三层来源:.env.example / .env / 真实环境变量
| 文件 | 入不入 Git | 作用 |
|------|-----------|------|
| `.env.example` | ✅ 入 | **配置说明书**:别人知道要配哪些变量(人写的文档,程序不读) |
| `.env` | ❌ 不入 | 本机真实值(`cp .env.example .env` 后改) |
| 真实环境变量 | — | 生产注入方式(Docker compose/k8s 直接设 env) |
**为什么 .env.example 要入库**:新人 clone 后 `cp .env.example .env` 填值就能跑。

### 3. ⭐ pydantic-settings 字段与环境变量的匹配规则(本迭代最大坑)
- 字段名 = 环境变量名,**默认大小写不敏感**匹配
- ✅ `db_host ↔ DB_HOST`(大小写差异,自动对上)
- ❌ `env ↔ APP_ENV`(还多了一个 `APP_` 前缀,**不认**→静默回退默认值)
- **记忆点**:环境变量名 = 字段名去掉大小写差异,**不能有多余前缀**
- **坑**:读不到不报错,**默默用默认值**——配置"不生效"极难排查
- **检测手段**:写测试覆盖"环境变量 > 默认值"的行为

### 4. BaseSettings 三个 model_config 参数
| 参数 | 作用 |
|------|------|
| `env_file` | 读哪个 .env 文件 |
| `env_file_encoding` | 文件编码(utf-8 因含中文注释) |
| `extra="ignore"` | 生产环境变量很多,不认识的**不报错**,忽略 |

### 5. ⭐ @lru_cache 单例
每次 `Settings()` 都读 .env 文件(I/O),热路径反复构造浪费。
`@lru_cache` 让 `get_settings()` 进程内只跑一次 → 只读一次 .env。

### 6. 字段是零件,URL 是成品
- 字段:`db_host`/`db_user`/`db_password`... 分散的零件
- 属性:`database_url` 属性把零件**拼装成成品**
- **装配逻辑只此一处**:阶段 1.3 拿到 URL 直接用,不会出现"别处手拼的 URL 不一致"

## 二、关键代码模式

| 模式 | 代码 | 用在哪 |
|------|------|--------|
| 配置说明书入 Git | `.env.example`(占位值,`#` 注释分组) | backend/ |
| 读 .env + 默认值 | `class Settings(BaseSettings)` + `model_config` | app/core/config.py |

| 全局单例 | `@lru_cache def get_settings()` | app/core/config.py |
| 环境变量 > 默认值测试 | `monkeypatch.setenv(...)` + `Settings()` | tests/test_config.py |

## 三、踩坑记录(自己写代码时遇到的)

1. **⭐ 字段名与环境变量名"大小写不敏感"但不做"前缀剥离"**:字段叫 `env`,环境变量写 `APP_ENV`,读不到,`Settings().env` 仍是默认 `"dev"`——**不报错,只表现为"配置没生效"**。这是生产级配置系统最隐蔽的坑之一。
2. **修复方式**:字段改名 `app_env`,与环境变量名大小写对齐;同时同步修改测试断言 `assert s.app_env == "prod"`。
3. **.env 路径要绝对定位**:`env_file=".env"` 是相对 CWD 的——不同目录跑指向不同文件(阶段 1.1 已提过)。本文件用 `BASE_DIR = Path(__file__).resolve().parent.parent.parent` 定位。
4. **测试里 `monkeypatch.setenv` 的 env 名必须跟字段完全对齐**(也适用上面第 1 条:`setenv("APP_ENV")` ↔ 字段 `app_env` 才行)。
5. **editor 编辑后未保存**:曾出现"修改完了"但磁盘时间戳不变、测试仍失败——用 `stat -c "%y"` 核对 mtime 来确认保存是否真正落盘。
6. **W293/空行尾随空格**:ruff 报空行里含空白 → `make format` 自动修。
7. **I001 import 排序**:ruff 要求 import 分组(标准库 → 第三方,之间空行)→ `make format` 自动修。

> 教训:**显示已保存 ≠ 磁盘已生效**;改完配置,测试是唯一的真相。

## 四、面试可能问

| 问题 | 答案要点 |
|------|---------|
| 配置管理最佳实践? | 代码只留默认值;真实值从 .env/环境变量注入;同一份 .env.example 跑 prod 时 export 覆盖 |
| pydantic-settings 原理? | BaseSettings 读 .env + 环境变量 + 字段校验,按固定优先级取值 |
| 环境变量优先级? | 真实 env > .env 文件 > 字段默认值 |
| 字段名和 env 名怎么对应? | 大小写不敏感;`db_host` ↔ `DB_HOST`;要有前缀需显式声明。**不能自带前缀**(`env` ↔ `APP_ENV` 读不到) |
| 为什么不直接 os.environ? | 手动 parse、无类型校验、电流无默认值;BaseSettings 自动做映射+类型转换+校验 |
| 如何确定配置"生效"? | 写测试(monkeypatch.setenv + 断言);改完配置跑 pytest,别信编辑器 |
| @lru_cache 作用? | 进程内单例,避免重复读 .env;修改配置后重启进程即可 |
| 数据库密码怎么存? | .env(本机)不入 Git;Docker/K8s 用环境变量注入;.env.example 只存占位 |
